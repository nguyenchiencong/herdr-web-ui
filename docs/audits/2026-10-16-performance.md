# Performance audit — 2026-10-16

Scope: the Bun bridge (`server/`), the React and xterm client (`src/`) and the wire contract
(`shared/`) at commit `364647b`. This audit only analyzed and measured. No source file was
changed. It looked for CPU hotspots, event-loop stalls, redundant herdr RPCs, leaks, React
re-render cascades and bundle weight, and it ranks fixes that keep every invariant in
[AGENTS.md](../../AGENTS.md):

- one herdr RPC connection per call, and one `events.subscribe` reopened with the full set
  (caching answers is allowed);
- no node-pty in Bun;
- no `--takeover` on the server's own initiative;
- xterm `scrollback: 0`, and an attached terminal is never rebuilt from `pane.read`;
- drafts are never sent automatically;
- selecting a pane never moves herdr's focus;
- `shared/herdr-api.generated.ts` is never edited.

Host: Windows 11 x64, 24 logical cores, Bun 1.4.3, Node 25.9.0, herdr 0.9.4-preview. On this
platform herdr has no `terminal attach`, so every terminal is a mirror (`server/mirror.ts`).
Linux and macOS figures in this audit come from micro-benchmarks of the same pure functions.
They are not live measurements.

## 2. Findings, ranked

Impact classes:

- **P0**: continuous waste that every user on a platform pays, or a main-thread stall that grows
  without bound.
- **P1**: a measurable hotspot on a common path.
- **P2**: a small or conditional gain.

"Unverified" marks a claim backed by code but not by a measurement.

### P0-1 Windows: a cold PowerShell process-table query about every 10 s whenever any pane exists

- **Evidence.** All PowerShell spawns in §1.2 come from native OmO discovery:
  - `OmoStatus.start` (`server/omo-status.ts:236-245`) calls `refresh` every `refreshMs` = 5 s,
    with no browser connected ("web push depends on it").
  - `refresh` runs `omoPanes(panes)` over **all** panes (`server/omo.ts:506-508`).
  - On win32, each pane's `processInfo` awaits `recentProcessTable()` (`server/omo.ts:337-342`).
  - That function spawns `Get-CimInstance Win32_Process … | ConvertTo-Json`
    (`server/windows-processes.ts:62-74`).
  - The table's cache is `PROCESS_TABLE_MS = 5000` (`server/gjc-runtime.ts:32`). A 1.5 s query
    plus 5 s cadence lands just past it, so most refreshes spawn again.
  - Measured: 3 spawns in 30 s with 5 plain shell panes and no OmO anywhere.
- **Cost.** Each spawn costs 2.3–2.5 s of CPU (§1.2). That is about 7 s of CPU per 30 s, or
  **about 24 % of a core, continuously, on every Windows install with at least one pane**. It does
  not count WMI's provider host. The same table also feeds `pi-subagents.ts:181`,
  `claude-store.ts:160/309` and `gjc-runtime.ts:61`, so those panes add to it.
- **Root cause.** A per-call PowerShell start (.NET runtime and CIM session) is used for a query
  that costs about 115 ms of CPU in a warm process. Discovery also re-reads the table on a timer
  when nothing about the panes has changed.
- **Fix, in order of payoff.**
  1. Run one long-lived PowerShell helper and send it a query line on stdin for each table read.
     This is about 20× less CPU per read. Respawn it on exit, give it a timeout, and kill it on
     `stop()`. Keep `windowsProcessTable` as the fallback.
  2. Trim the projection: drop `ExecutablePath` when `CommandLine` is present, and filter rows to
     descendants of the panes' `shell_pid`s inside PowerShell. The 255 KB JSON and Bun's parse of
     up to 31 ms both shrink.
  3. Skip the table entirely when no shell's child set can have changed. Key the refresh on
     `(pane_id, shell_pid, foreground pids)` from `pane.process_info`, and re-read the table only
     when that key changes or every 30 s.
- **Expected gain.** Idle Windows CPU falls from about 24 % of a core to about 1–2 % with (1),
  and to under 1 % with (1) and (3).
- **Risk.** OmO, GJC, pi and Claude detection on Windows relies on this table. A stale helper
  must be detected (a deadline on each answer). Detection latency for a newly started OmO must
  stay at 10 s or less.
- **Tests.** `server/gjc-runtime.test.ts:364-365` (`recentProcessTable` sharing),
  `server/windows-native.test.ts`, `server/omo.test.ts`, `server/omo-status.test.ts`,
  `server/omo-identity.test.ts`. Add a test that a helper answering slowly falls back to the
  one-shot query.

### P0-2 Unix attach: `ReplayBuffer.append` re-encodes the whole 128 KiB tail on every pty chunk

- **Evidence.**
  - `server/output-window.ts:155-172`: `Buffer.from(this.tail + data)`, then
    `bytes.subarray(start).toString("utf8")`, on every chunk.
  - It is called from `forward()` for every attached pty chunk (`server/index.ts:1350-1355`).
  - Measured: a constant of about 225 µs per chunk once the tail is full, whatever the chunk size.
    Throughput is capped at 0.3 MiB/s for 64 B chunks and 17 MiB/s for 4 KiB chunks
    (§1.3).
  - `text()` (the only reader that needs the trimmed tail) runs only when a client joins
    (`server/index.ts:3021`).
- **Cost.** Every TUI repaint, spinner tick or log line pays about 0.23 ms of event-loop time per
  attached pane: 60 chunks/s is about 14 ms/s per pane. A burst of small writes (an agent
  streaming tokens) saturates the loop and delays every other client's frames, ACKs and RPCs.
- **Fix.** Append chunks to an array and keep a UTF-8 byte count with `Buffer.byteLength`.
  Run the existing trimming algorithm only when the count passes 2 × `limit`, and once in
  `text()`/`recent`. The mode tracking still sees every cut byte in order, so `modes` and
  `modifyOtherKeys` are unchanged. The prototype returned byte-identical `text()`.
- **Expected gain.** About 750× less per small chunk (0.30 µs against 225 µs) and about 13× less
  at 4 KiB. Memory is bounded at 2 × 128 KiB per attachment.
- **Risk.** A cut can now land at a different chunk boundary. The `INCOMPLETE_CSI` back-off at
  the cut must keep its existing tests. `.recent` callers must go through the compacting
  accessor.
- **Tests.** `server/output-window.test.ts:225-260` (ReplayBuffer limits and modes),
  `server/output.contract.test.ts`, `server/reattach.contract.test.ts`, and
  `bun scripts/output-browser-qa.ts`.

### P1-1 Redundant `session.snapshot` RPCs: a full session dump to answer narrow questions

- **Evidence.**
  - Idle with no client: 18 `session.snapshot` in 30 s (0.6/s), three independent 5 s loops:
    - `machines.ts:200` `refreshLocal` → `clientSnapshot` → `omoSnapshot`;
    - the OmO timer, `omo-status.ts:240` → `deps.snapshot`;
    - the GJC timer, whose `snapshot` is `omoSnapshot` (`server/index.ts:1113-1117`).
  - Each mirrored attached pane adds one every `MIRROR_SIZE_MS` = 2 s, through
    `terminalInfoFor` (`server/index.ts:1205-1206`, `1312-1315`). The probe measured 12 → 22
    per 20 s with one viewer.
  - Every `/api/pane/conversation`, transcript-image and tool-output request starts with its own
    `sessionSnapshot()` (`server/conversation.ts:1435`, `1628`, `1674`), also for an answer that
    ends in 304.
- **Cost.** Each call opens a connection, makes herdr serialize every workspace, tab, pane and
  agent, and makes Bun parse it. It grows with session size × callers. The Bun-side CPU at 5
  panes was small (§1.2). The cost is herdr's, and it scales with sessions of 50+ panes
  (unverified at that size).
- **Fix.** Add one single-flight, short-TTL snapshot reader, for example 250–500 ms. It is shared
  by `omoSnapshot`, the GJC timer, `terminalInfoFor`'s size poll and the conversation resolvers,
  and is invalidated by every lifecycle event the collector already receives. This is caching an
  answer, which AGENTS.md allows, not connection reuse. For the mirror's size poll, read the rect
  from the collector's last snapshot and refresh it on `layout`/`pane.updated` events.
- **Expected gain.** Idle snapshots drop from 3 to 1 per 5 s. A mirrored viewer adds 0 instead of
  0.5/s. Conversation reads coalesce under bursts.
- **Risk.** Staleness. Anything that acts (attach, take-over, close) must keep a fresh read. Only
  observers may use the cache.
- **Tests.** `server/collector.test.ts`, `server/mirror.test.ts`,
  `server/conversation-push.contract.test.ts`, `server/machines-refresh.test.ts`,
  `server/pane-layout.contract.test.ts`.

### P1-2 OmO background-task count: synchronous read and parse of up to 2,048 files every second

- **Evidence.** `OmoStatus.poll` (1 s, `server/omo-status.ts:240`) calls `this.background(cwd)`
  for every tracked OmO folder (`:371`). The default is `omoBackgroundTasks`
  (`server/omo-status.ts:121-137`): `readdirSync` plus `readFileSync`/`JSON.parse` of every
  `st_*.json` file, up to 2,048, with no cache. Its sibling `omoTasks` caches by lstat key
  (`server/omo-tasks.ts:80-100`).
- **Cost.** On NTFS this blocks the event loop for 8 ms at 100 records, 35 ms at 500 and 211 ms at
  2,048 (§1.3), **every second, for each OmO folder**. How many task records OmO accumulates in
  practice is unverified.
- **Fix.** Reuse `omoTasks`'s per-file `(size, mtimeMs, ino)` cache, so only changed records are
  re-parsed. Skip the readdir when the `tasks/` directory's mtime is unchanged. Keep the
  `host_pid` liveness check per call; it is cheap.
- **Expected gain.** Steady state becomes one `statSync` of the directory per folder per second
  (< 0.1 ms).
- **Risk.** On some filesystems a directory's mtime does not change when a file inside is
  rewritten in place. The per-file lstat pass is the safe fallback.
- **Tests.** `server/omo-status.test.ts`, `server/omo-tasks.test.ts`, `server/omo-state-dir.test.ts`.

### P1-3 `machines.json` rewritten (fsync × 2) and the full roster pushed every 5 s, changed or not

- **Evidence.**
  - Each successful remote refresh (5 s per remote PC, `server/machines.ts:838`) calls
    `saveSoon()` without comparing (`:792`). `persist()` then writes the whole registry, remote
    snapshots included, with `writeFileAtomic` (`:432-437`). That is an fsync of the file and its
    directory (`server/state-file.ts:112-148`).
  - `refreshLocal` calls `emit()` after every 5 s read (`:402-426`). `emit()` sends the full
    `machines` list to every SSE subscriber (`server/machines.ts:372-375`,
    `server/machine-api.ts:61`).
  - Each browser JSON-parses that list and stringifies both copies to find they are equal
    (`src/App.tsx:90-92`, `:576`).
- **Cost.** 17,280 durable writes a day per remote PC on an idle system. Full-roster
  serialization goes out once per browser per 5 s, and every tab does two `JSON.stringify` passes
  over the roster on its main thread.
- **Fix.** Keep the last serialized registry and persist only when it differs. Keep the last
  emitted roster's JSON per MachineManager and `emit()` only on change, serializing once for all
  listeners.
- **Expected gain.** Disk writes at idle go to 0. SSE traffic at idle goes to heartbeats only.
- **Risk.** Low. Status patches still flow as `machine-message`.
- **Tests.** `server/machines.test.ts`, `server/machines-refresh.test.ts`,
  `server/machines-refresh.contract.test.ts`, `server/state-recovery.test.ts`.

### P1-4 Client: every 5 s the whole App re-renders, and a new `OpenFileContext` value re-renders every chat `Inline`

- **Evidence.**
  - `loadHealth` stores `setAuth(next.auth)` unguarded (`src/App.tsx:433`). `fetchBridgeHealth`
    returns a fresh object each 5 s tick (`src/App.tsx:454-471`, `POLL_MS`), so React re-renders
    `App` every tick while the page is visible.
  - `renderPane` builds a new provider value on each render:
    `<OpenFileContext.Provider value={item ? (path) => openFile(…) : null}>`
    (`src/App.tsx:1583`).
  - Context consumers bypass `memo`. Every `Inline` (`src/components/Markdown.tsx:173`),
    `CodeBlock` (`:243`), the ChatView consumers (`ChatView.tsx:240, 292, 330, 437`),
    `PaneTerminal` (`:177`) and `PromptCard` (`:118`) re-render, inside every mounted chat row.
  - `PaneCanvas`, `Sidebar`, `AgentSidebar`, `TabStrip` and `PaneTerminal` are not memoized.
- **Cost.** Unmeasured (needs a browser profile). On every tick, the chat repeats the
  inline-element construction of every visible message, even though `Markdown`'s parse stays
  memoized (`Markdown.tsx:326-327`).
- **Fix.**
  1. `setAuth((previous) => sameData(previous, next.auth) ? previous : next.auth)`.
  2. Memoize the per-pane open-file callback, for example a small `useMemo` map keyed by
     `(machineId, pane_id)`, or a `PaneOpenFileProvider` component with `useCallback`.
  3. Then `memo` `PaneCanvas` and `Sidebar`, after stabilizing their callback props.
- **Expected gain.** No App or chat render at all on an idle 5 s tick. Verify with the React
  Profiler: the commit count during 30 s idle should go from 6 to 0.
- **Risk.** Low. `auth` consumers must still see a real change (`reason` and `authenticated`).
- **Tests.** `bun run test:ui` (`scripts/ui-regression.ts`), `scripts/chat-browser-qa.ts`,
  `src/components/ChatView.test.tsx`.

### P1-5 Client: a changed conversation read rebuilds every turn object, so `memo(Turn)` never hits

- **Evidence.**
  - Each read JSON-parses a new page.
  - `showAnswer` stringifies the whole page to compare (`src/components/ChatView.tsx:984-988`)
    and then `setState(next)`, which holds all new turn objects.
  - `Turn` is `memo` with a comment saying an unchanged turn keeps its object
    (`ChatView.tsx:758-759`), but nothing preserves the object.
  - `renderTurn` depends on `shownTurns` (`:1492`), so every mounted row's `renderItem` reruns.
    `turnRevision(turn, true)` misses its WeakMap and re-hashes, including `JSON.stringify(part)`
    for every tool part (`src/lib/turnRevision.ts:11-30`).
  - This happens at most every 2 s during a live turn (`src/lib/conversationRefresh.ts`).
- **Cost.** Unmeasured. One full-page `JSON.stringify` (up to MBs) plus a re-render of every
  mounted row, per changed read.
- **Fix.** Share structure when an answer arrives. For each incoming turn, reuse the previous
  object when `turnRevision(prev) === turnRevision(next)`, matched by slot or id. Compare page
  signatures from those per-turn revisions instead of `JSON.stringify(next)`. Make `renderTurn`
  depend on a stable `shownTurns` lookup (a ref), passing `live` and `previousSettings` as
  props.
- **Expected gain.** Only the changed turn or turns re-render. The O(page) work per read is
  hashing only.
- **Risk.** `turnRevision` collisions (32-bit FNV). Include `parts.length` and timestamps, as it
  already does.
- **Tests.** `src/components/ChatView.test.tsx`, `src/lib/chatRows.test.ts`,
  `scripts/chat-virtual-browser-qa.ts`, `scripts/chat-history-browser-qa.ts`.

### P1-6 Bundle: all three locale dictionaries load for every user

- **Evidence.** `src/lib/i18n.ts:13-15` imports `JA`, `KO` and `ZH` statically. Together they are
  169.7 KiB of the entry chunk (11 %) and about 72 KiB brotli (§1.1). Only `resolvedLanguage`'s
  dictionary is ever read (`translate`, `:59-62`).
- **Fix.** Load each dictionary with `import()`. In `main.tsx`, await the dictionary for the
  initial `resolveLanguage(settings.language)` before `createRoot().render`. English needs none.
  A language change awaits its dictionary before `setCurrentLanguage`. `translate` keeps its
  English fallback while loading.
- **Expected gain.** About 15 % of the entry chunk. English users skip about 72 KiB br, and
  others about 48 KiB br.
- **Risk.** The first render must not flash English for a non-English user, which is why the
  await comes before render. `src/lib/i18n.test.ts` scans `t("…")` keys against the
  dictionaries and must import them directly.
- **Tests.** `src/lib/i18n.test.ts`, `scripts/settings-pages-demo-regression.ts`.

### P2-1 `pty-data` fan-out serializes the payload 2 × per client

`server/index.ts:1078-1089` (`sendOutput`) calls `wireBytes(data)`, which is
`JSON.stringify(data)` only to measure it (`server/output-window.ts:23-25`). Then `send()`
stringifies the whole message again (`server/index.ts:416`). Both run per client.

- **Measured:** 21 µs (1 client) to 115 µs (8 clients) per 4 KiB chunk, against 8 µs when the
  data is quoted once and spliced into each client's envelope (§1.3).
- **Fix:** In `forward()` and the mirror's `onData`, compute `bytes`, `quoted = JSON.stringify(data)`
  and `wire` once. Build `{"type":"pty-data","pane_id":…,"data":<quoted>,"flow":{…}}` per client
  with a string template, keeping `send()`'s budget checks.
- **Gain:** 2.7× at 1 client, 14× at 8.
- **Risk:** The envelope must stay byte-identical to `JSON.stringify` (field order is irrelevant
  to the client).
- **Tests:** `server/output.contract.test.ts`, `server/output-window.test.ts`.

### P2-2 Client per-chunk work in the xterm write callback

On each `pty-data` frame, `PaneTerminal.tsx:1114-1141` runs several steps after the write:

- `followCursor()`, which does `querySelector('.xterm-screen')` even when it returns early,
  `:710-718`;
- a `translateToString` walk of every buffer row (`:1126-1133`);
- `secretPrompt(lines.join("\n"))` (`:1137`).

`secretPrompt` only reads the bottom lines (`shared/secret-prompt.ts:2-16`), and
`scrollback: 0` bounds the walk to `rows`. It also sends one `pty-ack` per frame (`src/lib/ws.ts:676-686`).

- **Fix:**
  - Walk from the bottom up and stop at the first non-wrapped, non-empty line plus its wrap chain.
  - Cache the `.xterm-screen` element.
  - Coalesce ACKs. They are cumulative offsets, and the server's `OutputWindow.acknowledge` takes
    the max (`server/output-window.ts:70-77`), so sending the latest offset per animation frame
    keeps the semantics.
- **Gain:** Unmeasured. It is O(rows × cols) to O(cols) per frame.
- **Risk:** The ACK cadence feeds the stall detector (`OUTPUT_STALL_MS` = 2 s). A 16 ms coalesce
  is far below it.
- **Tests:** `shared/secret-prompt.test.ts`, `scripts/output-browser-qa.ts`,
  `server/output.contract.test.ts`.

### P2-3 Windows mirror: `pane.read` every 400 ms per idle mirrored pane

`MIRROR_IDLE_MS` (`server/mirror.ts:21`): 49 reads per 20 s idle were measured. Each `flush()`
also builds the whole `mirrorFrame` even when rows win (`:203-206`) and re-splits `this.sent`
(`rowsOf`). Both are small. The read rate is a deliberate echo-latency trade-off. Optional
changes:

- Relax the idle ceiling to 1 s after 10 s of no change and no input. `poke()` already gives
  echo reads 15 ms latency.
- Cache the previous rows array.

Tests: `server/mirror.test.ts`, `server/mirror-input.test.ts`.

### P2-4 Conversation requests do full resolution before a 304

`server/index.ts:2684-2699` computes `paneConversation()` first: snapshot, then
`agent.get`/`pane.process_info`, then stat, then the page cache. Only after that does it compare
`If-None-Match`. The response cache (`server/conversation.ts:1557-1620`) makes the read cheap,
but the RPCs stay. With P1-1's snapshot cache and a per-pane resolution memo keyed by
(foreground pid set, cwd) and kept 2–5 s, a 304 costs one stat. Tests:
`server/conversation-push.contract.test.ts`, `server/chat-read-timeout.test.ts`.

### P2-5 Synchronous gzip of API bodies

`server/compress.ts:54` runs `Bun.gzipSync` level 6 on the main thread for every `/api/` body over
1 KiB: 8.7 ms for a 2 MiB conversation page. Options:

- Use level 1 for `/api/` bodies over 512 KiB (3.7 ms, about 40 % larger).
- Use `CompressionStream`/`Bun.gzip` off-thread if a non-blocking API is available (verify on
  Bun 1.4).

Tests: `server/compress.test.ts`.

### P2-6 Bundle: lazy-load on-demand UI

Candidates: `SettingsDialog` (+ `DevicesPanel` → `QrCode` → `qrcode-generator`),
`CommandPalette`, the other dialogs, `voice.ts`/`VoiceInput`, and `ImageLightbox`/`FileViewer`.
That is about 180 KiB raw of the entry chunk (§1.1). `CommandPalette` imports `PAGES` from
`SettingsDialog.tsx:20`; move `PAGES` to a data module first. Also split `src/lib/highlight.ts`'s
engine and grammars from `languageForFence`/`CHAT_HIGHLIGHT_LIMIT`/`canHighlight`, which
`Markdown.tsx:8` needs eagerly. Use `lazyChunk` (`src/lib/lazyChunk.ts`) so a stale build
reloads instead of failing (`src/components/ChunkFailureNotice.test.tsx`).

The 264 KB CSS (46 KB br) goes with its components when they become lazy. Tests:
`scripts/settings-pages-demo-regression.ts`, `bun run test:ui`, and
`scripts/compressed-assets.test.ts` (sidecars).

### P2-7 Bundle: KaTeX twice

Mermaid 12.1 pins `katex ^0.16.47` while the app uses 0.18.9. A page with math inside a diagram
and in prose downloads both (259 KB raw each). Unverified: whether Mermaid works with 0.18. If it
does, a `package.json` `overrides` entry dedupes it. Test: `bun scripts/math-browser-qa.ts` plus
a Mermaid diagram with `$…$`.

### P2-8 `makeLineReader` is quadratic in frame length

`buffer.slice(index + 1)` and an `indexOf` over the whole growing buffer
(`server/herdr/client.ts:61-73`) cost 46 ms for a 4 MiB one-line answer, against 9.8 ms with a
chunk list (§1.3). Large answers are `pane.read` of history and big snapshots. Test:
`server/herdr/client.test.ts`.

### P2-9 Weakly bounded caches (slow growth, no observed leak)

- `server/files.ts:8`: one entry per cwd holding up to 5,000 paths, never evicted on expiry.
  Prune on `set`.
- `server/conversation.ts:454` `writtenSessions`: cleared only for panes still in `paneReads`.
- `server/omo-tasks.ts:22,100` `taskCache`: cleared only past 50,000 entries.
- `server/conversation.ts:1616`: the non-pi page cache has 32 entries and no byte budget.
  Each can be a 16 MiB window's parsed turns, so the worst case is several hundred MiB
  (unverified). Give it the pi path's byte budget (`:863`).

Tests: `server/files.test.ts`, `server/conversation.test.ts`, `server/large-history-agents.test.ts`.

### P2-10 Client: whole-App re-render per drag frame

The sidebar resizer calls `setSidebarWidth` on every pointer move (`src/components/SidebarResizer.tsx:59-67`,
`src/App.tsx:1493`). The tab drag publishes a new `{target, point}` object per move
(`src/lib/paneDrag.ts:33-35`) through `useSyncExternalStore` in App (`src/App.tsx:353`).

Fix: set a CSS variable on the shell during the drag and commit state on pointer up. Keep only
`target` in the store; the preview reads `point` from a ref.

Tests: `scripts/sidebar-activity-demo-regression.ts`, `src/lib/touchReorder` tests,
`scripts/ui-regression.ts`.

### Checked and found clean

- The server per-client maps are released on detach/close (`server/index.ts:1027-1041`,
  `1607-1616`).
- The collector's pane maps are pruned on reconcile.
- The client listeners and observers are balanced (App 12/12, PaneTerminal 24/24, ChatTimeline,
  ChatMinimap, VirtualSource).
- The client's hidden-tab polls stop.
- The SettingsProvider value is memoized (`src/lib/settings.ts:602`).

- `sw.js` precaches nothing.

### Re-measurement recipes

- **Bundle.** Run `bun run build` and list `dist/assets/index-*.js{,.br,.gz}` sizes. For
  attribution, rebuild with `--sourcemap` into a temp dir, then sum mapped generated bytes per
  `sources[]` entry by decoding the VLQ mappings (the throwaway `smattr.ts` did exactly that: per
  line, per segment, `bytes[source] += nextColumn - column`).
- **Bridge idle and mirror.** Under `CHECK_DIR=<short path> bun run check run bun <probe>.ts`:
  - wrap `Bun.spawn` and `Bun.connect` (count `argv[0]` and the `method` of each RPC frame);
  - import `scripts/test-herdr.ts`'s `useTestHerdr()`;
  - create N workspaces, then call `createServer({ port: 0, hostname: "127.0.0.1", token, stateDir: mkdtemp })`;
  - sample `process.cpuUsage()` over 30 s with no client, then with one WS `attach`.

  Never point it at the live session. On Windows, add the PowerShell CPU from `Get-Process` or
  the `Start-Process`/`TotalProcessorTime` recipe in §1.2.
- **Pure functions.** Use `Bun.nanoseconds()` loops over the exported function with warmed state.
  Report µs per call and payload MiB/s, as in §1.3. Run each 3 times and compare medians. On
  this host the ReplayBuffer runs varied by about 5 % (224.7–235.0 µs). Cold PowerShell wall
  time varied by about 25 % (1.3–1.7 s), and its CPU by about 8 %.
